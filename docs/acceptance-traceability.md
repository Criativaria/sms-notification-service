# PRD Acceptance Traceability

This matrix maps PRD functional requirements, reliability requirements, and Definition of Done (DoD) criteria to repository evidence. It distinguishes unit-test evidence, Docker-dependent integration test files, manual provider-sandbox verification, and unresolved gaps. A listed test is evidence of its stated behavior only; it does not imply full end-to-end acceptance.

## Evidence Status

| Status                                           | Meaning                                                                                                                                                                                                           |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Automated unit coverage                          | A Jest unit test exercises behavior with mocks or in-memory doubles.                                                                                                                                              |
| Automated integration coverage (Docker required) | A `*.int-spec.ts` test exercises live local infrastructure. Execution requires Docker Compose PostgreSQL/Redis and applied migrations; presence of the file does not claim it was run in the current environment. |
| Planned integration test                         | Required scenario with no corresponding Docker-backed integration test file.                                                                                                                                     |
| Manual sandbox verification                      | Requires real provider credentials and a temporary public callback URL.                                                                                                                                           |
| External blocker                                 | Cannot be verified as specified until the stated external dependency is available.                                                                                                                                |
| Gap recorded                                     | Current implementation behavior or verification does not establish the criterion.                                                                                                                                |

## Bird Local Mock Server

Bird Messaging is a paid API with no free sandbox for this project. Per the challenge author's
explicit clarification, mocking a provider from its official documentation is an accepted
approach, and mocking alone is sufficient when a real sandbox is not obtainable — so this mock
is the intended implementation for Bird, not a stopgap pending credentials. `mock-servers/bird/server.ts` is a small standalone Express server that:

- implements `POST /workspaces/:workspaceId/channels/:channelId/messages` (Bird's send endpoint), returning `200 { id: "bird-mock-<uuid>" }` and requiring a non-empty `Authorization: AccessKey ...` header;
- injects deterministic failures via `X-Mock-Force: retryable|permanent|timeout` (503, 400, or a hang, respectively) so failover/retry/DLQ scenarios and a live demo can be driven on demand;
- exposes `POST /simulate-callback/:messageId`, which signs a delivery payload with `BIRD_WEBHOOK_SIGNING_KEY` using the exact HMAC-SHA256 scheme `bird-signature.verifier.ts` expects and forwards it to the real service's `/webhooks/bird`.

It runs as the `bird-mock` service in `compose.yaml` (`docker compose up -d bird-mock`, port 8081) and is selected via `BIRD_API_BASE_URL=http://localhost:8081` in `.env`/`.env.example` — no code change is required to point `BirdProvider` at it instead of `https://api.bird.com`. Full contract and a failover/webhook demo script are documented in [`provider-sandbox.md`](provider-sandbox.md).

Verified live 2026-09-04: a real `POST /api/v1/sms/send` (with `SMS_PROVIDER_PRIORITY=bird`) dispatched through the running worker, landed `SENT` with a `bird-mock-*` provider message id, and a `simulate-callback` request produced a `200 {"status":"ok"}` from the real webhook verifier, moving the message to `DELIVERED`. Separately, with `SMS_PROVIDER_PRIORITY=twilio,bird` and Twilio failing definitively, the running app's logs showed `PROVIDER_ATTEMPT_FAILED provider=twilio` → `PROVIDER_FAILOVER` → `MESSAGE_SENT provider=bird`, and with both providers failing transiently, `MESSAGE_RETRY_SCHEDULED round=1`.

This is accepted per the challenge author's clarification as the sufficient implementation for
Bird in this project. The mock's webhook signature scheme, error-body shapes, and behavior are
built from Bird's publicly documented API, not independently re-verified against a live Bird
account, since none was required.

## Integration Test Inventory

`npm run test:integration` includes these Docker-dependent files (8 suites, 45 tests as of 2026-09-04):

1. `src/database/sms-persistence.repository.int-spec.ts`: live PostgreSQL atomic message/outbox/idempotency persistence and sequential key reuse.
2. `src/database/sms-lifecycle.repository.int-spec.ts`: live PostgreSQL provider-attempt reservation/finalization, including the definitive-failure release and ambiguous-outcome parking behavior.
3. `src/modules/queue/outbox-relay.service.int-spec.ts`: live PostgreSQL and Redis relay publication plus recovery from a simulated queue publish rejection.
4. `src/modules/queue/sms.processor.int-spec.ts`: live worker dispatch reliability — ambiguous timeout parking, definitive-failure failover within a pass, worker-scheduled retry rounds with backoff, exhaustion → DB-authoritative DLQ, requeue without a Redis DLQ job, DLQ notification completion/removal, and rate-limiter configuration.
5. `src/modules/providers/failover.int-spec.ts`: the `ProviderManager` layer directly, over real HTTP-stubbed Twilio/Bird strategies — retryable failover and the permanent-failure non-retry guard.
6. `src/modules/webhooks/webhooks.int-spec.ts`: signed Twilio/Bird webhook callbacks against the real running app and live PostgreSQL, including duplicate-callback no-ops and invalid-transition guards.
7. `src/modules/sms/sms.controller.int-spec.ts`: the real running app's `POST /api/v1/sms/send` over HTTP — validation, the private-network guard, and sequential/concurrent idempotency.
8. `src/modules/queue/dlq.controller.int-spec.ts`: the real running app's `POST /internal/dlq/:messageId/requeue` over HTTP against live PostgreSQL — successful requeue, the idempotent-requeue-rejects-twice case, and the private-network guard, mirroring the pattern in file 7.

Remaining scenarios not yet covered by an automated Docker-backed test:

1. Transactional outbox recovery after an actual Redis process outage/restart (only a simulated publish rejection is covered).
2. Worker/Redis crash-and-recover mid-flight (process kill, not simulated).
3. Real BullMQ throughput enforcement under concurrent load (only the limiter's configuration is asserted).
4. Durable retention-scheduler behavior across process restarts (the scheduler is now BullMQ-backed via `upsertJobScheduler`, but a restart-durability test does not exist yet).

See `to-do.md`'s "Plan to Resolve Remaining Gaps" for the prioritized fix plan covering the
metadata size limit, deterministic job IDs, and single-active-provider startup validation.
